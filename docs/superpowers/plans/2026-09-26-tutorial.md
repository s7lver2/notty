# Tutorial (welcome_window + tour) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first-run welcome window (guided steps, applied live) and the spotlight tour over the real UI, matching `docs/mockups/setup/tutorial.html` exactly.

**Architecture:** `welcome_window.rs` is a non-modal floating window in `notty-ui`, built the same way as `settings_window.rs` (own wndclass/wndproc, reuses `Renderer`, radios/segmented controls from `settings_model.rs`'s row types). `tour.rs` is not a window — it's an overlay layer painted directly by the main window (`window.rs`) using `layout::frame()`'s `Frame` rects to know where to put the spotlight, so it automatically matches whichever layout mode (modern/classic) is active.

**Tech Stack:** Rust, existing `notty-ui`/`notty-config` machinery — no new dependencies.

## Global Constraints

- Every step's choice applies live: writing to `Config` and triggering the same repaint/theme-change animation notty already uses when Ajustes changes a value.
- Motion: step transitions 140ms out / 180ms in / 12px (same as the installer), spotlight move-and-reshape 450ms, checkmark stroke 600ms (welcome window's own "Listo" step, same technique as the installer's Listo screen).
- Respect `system_animations_enabled()` (now `pub`, from the installer plan) via `Anim::new_maybe` everywhere.
- Visual fidelity to `docs/mockups/setup/tutorial.html` is mandatory — open it in a browser and compare copy, colors, spacing, and the spotlight/tooltip look against the running app.
- `first_run_done` and tour trigger logic must not add any network dependency (unrelated to the updater plan, do not couple them beyond both touching `Config`).

pub struct StepRail {

    pub current: usize,

impl StepRail {

### Task 4: `tour.rs` — spotlight overlay

**Files:**
- Create: `crates/notty-ui/src/tour.rs`
- Modify: `crates/notty-ui/src/window.rs` (paint the overlay when a tour is active, route `WM_LBUTTONDOWN`/`WM_KEYDOWN` to it first)
- Modify: `crates/notty-ui/src/lib.rs` (add `pub mod tour;`)

**Interfaces:**
- Consumes: `layout::Frame` (per the survey: `titlebar, settings_btn, caption_min/max/close, menubar, tabs_below, body, hints, status` rects), `keymap`/`command` constants for the shortcut labels shown (`Ctrl+T`/`Ctrl+W` note: per the survey Ctrl+T is unbound and Ctrl+N is "new tab" — see Step 1 below, this is a spec/code mismatch to resolve, not to silently paper over).
- Produces: `pub struct Tour { stops: Vec<Stop>, current: usize, anim: Option<Anim> }`, `pub fn start(frame_provider: impl Fn() -> Frame) -> Tour`, `pub fn draw(&self, renderer: &Renderer, frame: &Frame, now: Instant)`, `pub fn advance(&mut self)`, `pub fn handle_key(&mut self, vk: u32) -> TourInput` (`Esc`/click-outside close it).

- [ ] **Step 1: Resolve the Ctrl+T/Ctrl+W stop against real keybindings**

The spec's tour stop "Pestañas (Ctrl+T/Ctrl+W)" assumes Ctrl+T opens a new tab, but the actual binding is **Ctrl+N** (`crates/notty-input/src/command.rs:22` area, `UiCommand::NewTab`); Ctrl+W is correctly `CloseTab`. Use the real binding: the tour stop's copy must say **"Ctrl+N / Ctrl+W"**, not "Ctrl+T/Ctrl+W" as mockup copy may show — check `docs/mockups/setup/tutorial.html` for the literal string used there and correct it to match the real shortcut if the mockup also says Ctrl+T (mockups were written before this check; code truth wins over stale mockup copy for keybindings specifically, not for visual style).

- [ ] **Step 2: Define stops from `Frame` fields**

- [ ] **Step 3: Implement the sliding/reshaping spotlight**

`draw()`: dims the whole window with the mockup's `rgba(10,10,12,.62)` veil, cuts a rounded-rect hole at the current stop's `rect(frame)`, animating both position and size over 450ms when moving between stops (`Anim::new_maybe(transition_start, Duration::from_millis(450), animations_enabled)`, interpolating each of x/y/width/height between the previous and next stop's rect via `Anim::value`). The tooltip follows the spotlight, showing `title`/`body`/`kbd` chips styled like the mockup's `<kbd>`-style tags, plus progress dots and "Siguiente →"/"← Atrás".

- [ ] **Step 4: Wire into `window.rs`**

Add an `Option<Tour>` field to the main window's state struct. In the paint handler, after the normal UI paint, if a tour is active call `tour.draw(...)` last so it overlays everything. Route `WM_KEYDOWN`'s `Esc` and a global `WM_LBUTTONDOWN` (click outside the current spotlight rect closes the tour) to `tour.handle_key`/a click-outside check, before any other key/click handling, while a tour is active.

- [ ] **Step 5: Trigger points**

- On normal startup, if `!config.first_run_done`, show the welcome window (not the tour directly) before the first paint settles, per spec.
